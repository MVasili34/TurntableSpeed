# 6. Акустика: отклонение строя — быстро, но с оговоркой

Код: `Estimators/PitchGridEstimator.cs`, `Dsp/PhaseMath.cs` (круговая статистика)

---

## 6.1. Идея и её фундаментальное ограничение

> Матчасть — равномерная темперация, сетка полутонов, центы, гармоники — разобрана в
> [00-Теория-звука.md](00-Теория-звука.md). Особенно §0.6–0.8.

Если проигрыватель идёт в `(1+e)` раз быстрее, все частоты записи умножаются на `(1+e)`.
Западная музыка почти всегда написана в равномерной темперации: частоты нот сидят на
логарифмической сетке с шагом полутон = `2^(1/12)`. Значит можно посмотреть, **насколько
музыка отстоит от этой сетки**, и получить отклонение — за секунды, без всяких щелчков.

Метод даёт результат мгновенно и годится для живой индикации.

### Оговорка, которая не устраняется

Метод измеряет **высоту того, что напрессовано на пластинку**, а не скорость диска.
Слагаемых как минимум три:

```
измеренное_отклонение = ошибка_проигрывателя
                      + строй_записи (группа могла играть не в 440 Гц)
                      + дрейф_мастеринга (ленточный магнитофон, скорость нарезки)
```

Исторические факты, делающие это реальной проблемой: до стандартизации A=440
использовались 435, 432, 444 Гц; ленточные машины при сведении уходили; многие
классические записи 60-х заметно отклоняются от 440.

Разделить эти слагаемые изнутри записи **невозможно** — это не недоработка алгоритма, а
свойство задачи.

Поэтому в коде:

```csharp
public const string Caveat =
    "Pitch deviation mixes the turntable's speed error with the record's own tuning: ...";
```

и константа

```csharp
RecordTuningUncertaintyCents = 15.0    // систематика, всегда в σ
ConfidenceCeiling = 0.5                // потолок уверенности
```

15 центов ≈ 0.87 % — это оценка типичного разброса строя реальных записей. Она **входит в
отчётную σ**, поэтому при слиянии по обратным дисперсиям этот оценщик автоматически
получает малый вес против автокорреляционного, вместо того чтобы выигрывать своим узким
статистическим интервалом. В диагностику всегда пишется флаг `mixesRecordTuning = 1`,
чтобы UI не мог показать число без предупреждения.

## 6.2. Кадровый анализ

| Параметр | Значение | Обоснование |
|---|---|---|
| Длина кадра | 4096 | при 48 кГц — 85 мс, разрешение 11.7 Гц |
| Хоп | 50 мс | требование спецификации, перекрытие ~40 % |
| Окно | Ханна | компромисс между шириной главного лепестка и подавлением боковых |
| Полоса | 100–4000 Гц | ниже — бины слишком грубы; выше — партиалы плотнее полутона |

Кольцевой буфер накапливает отсчёты; каждые `hop` отсчётов выпускается кадр.

**Метка времени кадра ставится на его середину**, а не на конец. Ниже по потоку эти
метки использует спектр детонации ([07](07-Детонация.md)), а ему важно, *когда звучала
музыка*, а не когда заполнился буфер. Ошибка в полкадра (43 мс) на частоте 0.556 Гц —
это 8° фазы, что уже заметно.

Обработка кадра:

```
1. RMS кадра (для веса и индикатора уровня)
2. вычесть среднее          (убрать постоянную составляющую)
3. умножить на окно Ханна
4. FFT → амплитудный спектр
5. поделить на когерентное усиление окна (0.5 для Ханна)
```

Деление на когерентное усиление возвращает истинные амплитуды: окно Ханна ослабляет
сигнал вдвое, и без коррекции синус амплитуды A читался бы как A/2.

Разрыв в потоке (>50 мс или полблока) очищает буферы: пропуск аудио создал бы ложный
разрыв в ряде центов, который спектр детонации принял бы за модуляцию.

## 6.3. Свёртка спектра на один полутон

### Почему пики, а не все бины

Бин между партиалами несёт **утечку спектра** (боковые лепестки окна), а не высоту тона.
Включив все бины, мы разбавили бы оценку шумом. Поэтому берутся только локальные максимумы
амплитудного спектра.

Отбрасываются пики слабее `2 %` от сильнейшего в кадре, и оставляются максимум 40
сильнейших: плотный шумный спектр иначе размыл бы круговое среднее.

### Уточнение частоты пика — по логарифму амплитуды

```csharp
var refined = PeakInterpolation.Parabolic(
    Log(amplitudes[index - 1]),
    Log(amplitudes[index]),
    Log(amplitudes[index + 1]));
```

Это существенно. Главный лепесток окна Ханна в **логарифмическом** масштабе близок к
параболе (по форме напоминает гауссиан, у которого логарифм — точная парабола), а в
линейном — нет. Интерполяция по log-амплитудам даёт заметно меньшее смещение.

Точность здесь принципиальна: при разрешении 11.7 Гц и частоте 440 Гц один бин — это
46 центов. Без субсэмплового уточнения метод не имел бы смысла вообще.

### Перевод в отклонение от сетки

```
полутонов_от_A4 = 12 · log₂(f / 440)
центы = (полутонов − round(полутонов)) · 100
```

Округление до ближайшего целого полутона убирает информацию о том, *какая* это нота, и
оставляет только отклонение от сетки, свёрнутое в **(−50, +50] центов**.

Именно поэтому метод работает на любой музыке, не зная тональности: все ноты
равномерно-темперированного строя дают одно и то же отклонение от сетки.

### Вес пика

```
w = log(1 + A/threshold)
```

Логарифмический вес, как и требует спецификация. Смысл: громкий бас не должен перевесить
весь остальной аккорд. Линейный вес отдал бы 90 % голоса самому сильному партиалу;
логарифм уравнивает вклад громких и тихих, не обнуляя разницу совсем.

## 6.4. Круговое среднее: почему обычное не годится

Отклонения свёрнуты в (−50, +50]. Величина **циклическая**: +49 и −49 центов — это почти
одно и то же (расстояние 2 цента через границу), а не разница в 98.

Обычное среднее здесь даёт бессмыслицу. Классический пример: два пика на +49 и −49.
Арифметическое среднее = 0, тогда как истинное среднее ±50.

Правильный инструмент — **круговая статистика**. Значения переводятся в углы, усредняются
как единичные векторы:

```
θᵢ = центыᵢ · 2π/100

C = Σ wᵢ cos θᵢ / Σ wᵢ
S = Σ wᵢ sin θᵢ / Σ wᵢ

θ̄ = atan2(S, C)                      круговое среднее
R = √(C² + S²)                        результирующая длина, 0..1
центы = θ̄ · 100/(2π)
```

Код: `PhaseMath.CircularMeanOverPeriod` — обобщение на произвольный период вместо 2π.

### Результирующая длина как мера качества

`R` — это длина среднего единичного вектора:

* `R → 1` — все углы сосредоточены, оценка надёжна;
* `R → 0` — углы разбросаны равномерно, среднее направление **не определено**.

Это ключевая диагностика: `R` близкое к нулю означает, что в кадре не было тональной
музыки (ударные, шум, тишина), и его значение центов не значит ничего. Кадры с
`R < 0.15` не участвуют в усреднении вовсе.

### Круговое стандартное отклонение

```
σ_угл = √(−2·ln R)
σ_центы = σ_угл · 100/(2π)
```

Стандартный результат круговой статистики: для распределения фон Мизеса при большой
концентрации `R ≈ exp(−σ²/2)`, откуда `σ = √(−2 ln R)`. Формула аккуратно расходится к
бесконечности при `R → 0` — что верно: при полном разбросе неопределённость бесконечна.

## 6.5. Усреднение по кадрам и честная статистика

Кадры собираются в окно 6 с, усредняются тем же круговым средним с весами `R²`
(квадратичный вес: концентрированный кадр заслуживает непропорционально большего доверия).

### Поправка на перекрытие кадров

Кадры длиной 85 мс идут с хопом 50 мс — они **перекрываются на 40 %**. Соседние кадры
частично содержат одни и те же отсчёты, значит не независимы. Считать их все за
независимые наблюдения — занизить интервал.

```
n_эфф = span_окна / длительность_кадра        (не число кадров!)
σ_стат = σ_центы / √n_эфф
```

То есть считаются только **непересекающиеся** кадры. При окне 6 с и кадре 85 мс это 70
вместо 120 фактических кадров.

### Итоговая σ

```
σ_итог = √( σ_стат² + 15² )
```

15 центов — систематика строя записи. При типичной `σ_стат` в единицы центов **систематика
доминирует полностью**, и это правильно: сколько ни усредняй, неизвестность строя записи
не уменьшится.

## 6.6. От центов к rpm

Оценщик измеряет **отклонение**, а не скорость. Чтобы выдать rpm, нужно знать, от какого
номинала это отклонение — а высота тона отличить 33⅓ от 45 не может в принципе (запись,
проигранная на 45 вместо 33⅓, звучит на 35 % быстрее = 5.2 полутона, что просто
транспонирование в другую тональность; сетка полутонов при этом остаётся сеткой).

Поэтому `AssumedNominal` приходит извне — от автокорреляционного оценщика или от
пользователя. Без него `Current` остаётся `null`, но индикация в центах живёт.

```
относительное = 2^(центы/1200) − 1
rpm = rpm_номинала · (1 + относительное)
```

### Перенос погрешности

Нужна производная:

```
d(относительное)/d(центы) = (ln2/1200) · 2^(центы/1200)
```

Вывод: `относительное = 2^(c/1200) − 1`, значит
`d/dc = 2^(c/1200) · ln2 / 1200`.

```
σ_rpm = rpm_номинала · (ln2/1200) · 2^(центы/1200) · σ_центы
```

Производная берётся **в точке измерения**, а не как константа — потому что зависимость
экспоненциальная, и при больших отклонениях `2^(c/1200)` заметно отличается от 1. Для
малых отклонений это сводится к привычному `σ_rpm ≈ rpm · σ_центы/1731`.

## 6.7. Уверенность

```
concentration = (R − 0.2)/0.6              есть ли вообще тональный материал
precision     = 1 − σ_стат/10              статистическая точность
coverage      = usableFrames/100           накоплено ли достаточно кадров

confidence = (concentration · precision · coverage)^(1/3) · 0.5
```

Множитель `0.5` — **жёсткий потолок**. Как бы концентрированно ни сидела высота тона,
строй записи неизвестен. Оценщик не имеет права претендовать на высокую уверенность.

## 6.8. Итог

```
аудио
   ↓
кольцевой буфер 4096, хоп 50 мс, метка на середине кадра
   ↓
вычесть среднее → окно Ханна → FFT → амплитуды / когерентное усиление
   ↓
локальные максимумы в 100–4000 Гц, сильнее 2 % от максимума, до 40 штук
   ↓
уточнение частоты параболой ПО ЛОГАРИФМУ амплитуды
   ↓
центы = (12·log₂(f/440) − round(...)) · 100 ∈ (−50, +50]
   ↓
круговое среднее по кадру с весами log(1 + A/thr) → (центы_кадра, R)
   ↓
окно 6 с, круговое среднее по кадрам с весами R², отбрасывая R < 0.15
   ↓
σ = √( (σ_кругл/√n_непересек)² + 15² )        ← систематика строя доминирует
   ↓
rpm = номинал·(1 + 2^(c/1200) − 1),  потолок уверенности 0.5
```
